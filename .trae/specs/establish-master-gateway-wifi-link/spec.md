# 主从 Wi-Fi 通信（主机唯一网关）Spec

## 为什么

主机 ESP32Stat 实物只引出 ADC/C1/C2/DAC、VBAT/GND、WE/RE/CE，没有可用的 UART/GPIO 排针，现有 `Serial2(32/33)` 方案无法接线；从机 ESP32E 与主机均具备 2.4 GHz Wi-Fi，因此改用 Wi-Fi 承载现有 JSON 行协议。

架构上选择**主机唯一网关**：浏览器只连主机，主机负责采集、实验调度和从机控制，从机只执行泵/阀。这样无人值守时实验不依赖 PC 或浏览器，状态只有一个权威来源，也保留了原 NanoStat“PC 只连主机”的使用方式。

## 架构决策

- **采用**：主机 APSTA（`NanoStatAP` 常开）+ TCP Server；从机 STA + TCP Client 主动连接主机；网页只连主机。
- **不采用**：两块板都连 PC/同一网络、网页同时直连两块板。原因：
  - 调度会落到浏览器，PC 休眠、浏览器关闭或标签页限流都会中断 12–72 h 实验；
  - 多标签页/多人操作会产生重复命令与状态冲突；
  - 从机需额外运行 Web 服务，增加内存、代码量和攻击面；
  - 原 NanoStat 单设备网页需要改造成多设备仪表盘。
- **从机调试**：保留 USB 串口，用于不接主机时的脱机自测；本变更不给从机增加 Web UI。

## 变更内容

- 主机 Wi-Fi 从“STA 或 AP 二选一”改为 **APSTA**：AP 常开供从机连接，STA 可选连实验室路由器供用户访问。
- 主机新增 TCP Server（3333），用 `WiFiClient` 替换 `Serial2` 作为从机链路；现有 `slaveSend()` / `slaveLoop()` 的协议解析和网页转发逻辑保留。
- 从机新增 Wi-Fi STA + TCP Client，保留 USB 串口；命令可从 USB 或 TCP 进入，响应回到发起命令的通道。
- 协议继续使用 JSON 行格式，新增 `hello` 事件（携带固件版本、通道数、共享 key）。
- **BREAKING**：移除 UART2 作为运行链路的依赖；主机不再初始化 `Serial2` 连接从机。
- **BREAKING**：泵命令不再允许 `ms=0` 常开，主机改发有限时长，从机拒绝 `ms<=0`。
- 修复从机心跳超时后每个循环重复上报 `fault` 的现有缺陷。
- 主机网页增加从机链路在线状态；从机离线时拒绝启动实验。

## 影响

- 受影响能力：主从通信、实验调度、执行器安全、网页状态显示、部署与调试流程。
- 受影响代码：
  - `src/main.cpp`：Wi-Fi APSTA、TCP Server、`slaveSend()` / `slaveLoop()`、`expPumpRun()`、`serviceExperiment()`、`expStart()`。
  - `slave/slave_firmware.ino`：Wi-Fi STA、TCP Client、`hello`、双通道收发、心跳缺陷修复、`pump` 参数校验。
  - `data/panel.html`、`data/websckt_ctl_pan_LMP91000.js`：从机链路状态显示。
  - `.gitignore`、`README.md`、`docs/开发方案.md`、`docs/软件需求说明书.md`、`docs/项目进度总结.md`：凭据与文档同步。
- 不改硬件，不改泵/阀引脚分配。
- 设计细节与代码骨架见 `docs/主从WiFi通信开发文档.md`。

## 新增需求

### 需求：主机作为唯一网关

主机必须工作在 APSTA 模式，SoftAP `NanoStatAP` 常开；从机必须以 STA 身份连接该 AP，并以 TCP Client 身份主动连接主机 3333 端口。浏览器只能连接主机；本变更中从机不得提供 HTTP/WebSocket 服务。

#### 场景：上电自动入网

- **WHEN** 主机上电并启动 AP 与 TCP Server，从机上电
- **THEN** 从机在 15 s 内连上 `NanoStatAP` 并建立 TCP 连接
- **AND** 从机发送 `hello`，主机记录从机在线

#### 场景：从机不经主机无法被网页控制

- **WHEN** 浏览器只连接主机，尝试访问从机
- **THEN** 从机没有可用的网页控制入口
- **AND** 所有泵/阀操作只能经主机转发

### 需求：链路建立与 `hello` 鉴权

从机连接成功后必须发送 `{"evt":"hello","fw":...,"channels":...,"key":...}`。主机必须校验 `key`，校验失败立即断开；校验通过后才把从机标记为在线，并要求从机返回 `status` 快照用于对账。主机同时只允许一个从机客户端，第二个连接必须被拒绝。

#### 场景：正确 key

- **WHEN** 从机发送带正确 key 的 `hello`
- **THEN** 主机标记链路在线，发送 `status` 请求对账
- **AND** 网页显示从机在线

#### 场景：错误 key 或第二个客户端

- **WHEN** 从机发送错误 key，或第二个客户端连接 3333
- **THEN** 主机立即关闭该连接
- **AND** 不执行该连接发来的任何命令

### 需求：JSON 行协议兼容

TCP 链路必须继续使用“一行一个 JSON、`\n` 结尾、单行不超过 512 B”的格式；现有 `ping`、`pump`、`valve`、`stop_all`、`status`、`clear` 命令及其响应/事件语义保持不变。新增的 `hello` 是唯一新增事件。

#### 场景：现有命令行为不变

- **WHEN** 主机经 TCP 发送 `pump`、`valve`、`stop_all`
- **THEN** 从机动作与响应与 USB 串口测试一致
- **AND** 响应带同一 `id`

### 需求：心跳、断线检测与重连

主机在链路在线期间必须每 5 s 发送一次 `ping`，空闲阶段也不得停发。从机 120 s 未收到任何命令必须进入安全态（停泵、关阀）并上报 `E_NO_HEARTBEAT`，同一超时周期只上报一次。从机断线后必须按 1/2/5/10/30 s 退避重连；主机在 socket 断开或 20 s 未收到从机消息时标记离线。重连成功后必须重新 `hello` 并做 `status` 对账。

#### 场景：空闲不误报

- **WHEN** 实验处于 IDLE，主机与从机链路正常
- **THEN** 主机持续每 5 s 发 `ping`
- **AND** 从机不进入安全态、不产生 `fault`

#### 场景：主机静测阻塞

- **WHEN** 主机执行 `runAmp()` 阻塞约 60 s
- **THEN** TCP 连接保持，不因主循环停摆而断开
- **AND** 从机在 120 s 内不误判心跳超时

#### 场景：断线恢复

- **WHEN** 主机重启或 AP 换信道导致从机掉线
- **THEN** 从机在 15 s 内自动重连
- **AND** 重连后主机用 `status` 恢复泵/阀真实状态

### 需求：执行器安全与有限时长

主机发送泵命令时必须使用有限时长（循环阶段为 `circulate_ms + 60 s`），不得使用 `ms=0`。从机必须拒绝 `ms<=0`，保留泵 1 h 上限与阀 30 s 上限。网络发送不得阻塞执行器定时；发送缓冲不足时丢弃本次状态上报。链路断开时，从机按本地定时继续执行，到期后自动停。

#### 场景：循环中断线

- **WHEN** 循环均质阶段 Wi-Fi 断开
- **THEN** 泵在“设定循环时长 + 60 s”内自动停止
- **AND** 阀在 30 s 内关闭

#### 场景：非法泵参数

- **WHEN** 主机或调试者发送 `ms=0` 或超上限的泵命令
- **THEN** 从机回 `E_PARAM`
- **AND** 泵不启动

### 需求：网页状态与启动保护

主机必须通过现有 WebSocket 向网页广播从机链路状态（至少在线/离线），并保留现有实验阶段、周期、泵/阀状态显示。从机离线时，主机必须拒绝启动实验并在网页给出提示。

#### 场景：从机离线启动实验

- **WHEN** 从机不在线，用户在网页点击“启动实验”
- **THEN** 主机不进入实验流程
- **AND** 网页显示从机离线提示

#### 场景：链路状态可见

- **WHEN** 从机连上或断开
- **THEN** 网页上的从机链路状态在 1 s 内更新

### 需求：凭据与访问安全

主机 AP 必须默认启用 WPA2 密码；从机连接密码必须与 AP 密码一致。AP 密码、从机 Wi-Fi 凭据和 `hello` 共享 key 必须放在不入库的凭据头文件中。若现场确需开放 AP，必须显式配置，并强制启用 `hello` key 校验和单客户端限制。

#### 场景：仓库不泄露凭据

- **WHEN** 提交代码
- **THEN** AP 密码、从机 Wi-Fi 密码、link key 不出现在版本库中

### 需求：从机心跳缺陷修复

从机心跳超时进入安全态后，必须重新武装超时计时或使用“已上报”标志，确保同一超时周期只上报一次 `fault`，不得每个 `loop()` 重复上报。

#### 场景：心跳超时只报一次

- **WHEN** 从机连续 120 s 未收到命令
- **THEN** 从机停泵关阀并上报一次 `E_NO_HEARTBEAT`
- **AND** 在下一条有效命令到达前不重复刷屏

### 需求：脱机调试通道保留

从机必须保留 USB 串口，可在不接主机时用串口助手完成 `ping/pump/valve/stop_all/status/clear` 自测；USB 与 TCP 双通道同时可用时，响应必须回到发起命令的通道。

#### 场景：不接主机自测

- **WHEN** 从机只接 USB，不连主机
- **THEN** 串口助手可正常收发全部命令

## 修改的需求

### 需求：主从物理链路

原需求为 UART 115200、8N1、3.3 V、共地，主机 GPIO32/33 与从机 GPIO32/33 交叉连接。现修改为：主机 SoftAP + TCP Server，从机 STA + TCP Client，应用层 JSON 协议保持不变。

### 需求：主机 Wi-Fi 模式

原需求为 STA 连接路由器，失败时切换为 AP。现修改为 APSTA：AP 始终开启供从机连接，STA 可选连接路由器供用户访问；STA 失败不得关闭 AP。

### 需求：从机通信接口

原需求为 USB 调试口 + `Serial2` 主机口。现修改为 USB 调试口 + TCP 主机链路；`Serial2` 不再作为主链路。

### 需求：泵运行时长

原需求允许 `ms=0` 表示常开。现修改为只允许有限时长，`ms<=0` 视为非法参数。

## 移除的需求

### 需求：UART2 板间链路

**原因**：主机 ESP32Stat 实物未引出 UART/GPIO 排针，`GPIO32/33` 无焊盘可接，UART 方案不可实施。

**迁移**：改用 Wi-Fi TCP 承载同一套 JSON 行协议；主机删除 `Serial2` 初始化与收发，从机保留 `Serial2` 代码仅作历史/台架备用，不参与运行链路。

## 验收标准

- 主机 AP 常开；AP 就绪后，从机上电 15 s 内自动入网并显示在线。
- TCP 上 `ping/pump/valve/stop_all/status/clear` 行为与 USB 串口一致。
- 空闲阶段主机每 5 s 发心跳，从机不误进安全态。
- 循环中断线，泵在“循环时长 + 60 s”内停，阀 ≤ 30 s 关；恢复后 15 s 内重连并完成状态对账。
- `ms=0` 被从机拒绝；心跳超时只上报一次 `fault`。
- 错误 key、第二个客户端被拒绝。
- 网页显示从机链路状态；从机离线时无法启动实验。
- 24 h 连续运行无死机/复位，命令成功率 ≥ 99.9%。
- EMI 对比实验（从机断电/仅 USB/Wi-Fi 空闲/Wi-Fi 压力/泵运行）无可辨识的基线恶化。
